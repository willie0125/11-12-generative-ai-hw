# 可靠性、限制與何時使用

## Agent 可能在哪裡出錯

- **理解任務錯誤**：漏掉限制條件或誤解使用者意圖。
- **選錯工具或參數**：呼叫不適合的工具、查詢範圍不對。
- **誤讀回傳結果**：把過期、部分或含糊的資料當成確定答案。
- **過度繼續**：重複呼叫工具、耗費時間或成本，甚至嘗試不該做的事。
- **權限設計不足**：高影響動作沒有確認點。

ReAct 提供行動和觀察交替的研究例子，但觀察回饋本身並不保證模型判讀正確。[S03] Agent SDK 文件將 guardrails、human review、trace 和 evaluation 納入建置指引。[S04]

## 實用檢查

1. 定義任務完成條件與停止界限（最大步數、時間或成本）。
2. 對外部行動設定最小權限；有不可逆或高影響操作時要求確認。
3. 將重要答案追到來源或工具結果，標出不確定部分。
4. 保留執行 trace，透過實際案例評估錯誤，再修改提示、工具或流程。
5. 如果固定 Workflow 已能穩定完成任務，就不必因為 Agent 聽起來更聰明而增加自主性。[S02][S04]

## 什麼時候值得使用

當任務需要跨多個步驟、根據外部資訊變化調整做法，而且錯誤可以被發現或控制時，Agent 可能有幫助。若任務很固定、要求零延遲、沒有可用的覆核方式，或單次錯誤代價很高，應先考慮更簡單的 Workflow 或人工決策。Agentic 系統可能以更高延遲和成本換取任務表現，這是設計取捨而非保證。[S02]

## 概念邊界

MCP 可以標準化應用連接外部資料和工具的方式，但不代表外部資料正確，也不會取代應用本身的授權、審核和安全設計。[S05]
